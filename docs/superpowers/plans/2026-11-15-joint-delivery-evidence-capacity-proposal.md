# Joint Delivery Contract and Evidence Capacity Revision Proposal

> **For agentic workers:** 仅供 Owner 审核。只有另行明确批准的阶段才能使用
> superpowers:executing-plans 执行；不启动独立评审代理，不据本文开始实现或测试系列。

**Goal:** 提出一个交付域、完整证据预算和验证义务相互匹配的单一容量修订候选，
在 live 1 MiB 不变时消除已知反例的根因，或者明确剩余不可行条件。

**Architecture:** 候选沿原 v4 JSONL 的逐记录提交和全历史审计语义，不采用失败 v6
事务候选，不合并 read/提交/审计。新增可证明的接收端交付契约与分通道证据预算，
所有新限制作为环境协议修订显式审批。先证明，再考虑实现；不承诺当前可采集。

**Tech Stack:** 当前研究 Node/JSONL/SSE 接口与冻结材料；有界交付客户端尚未选定或
验证。本文不声称 native Fetch、highWaterMark、BYOB 或接收后切片自动提供所需保证。

**Spec:** [S2 已认可审议](../../../research/phase-0.9.19/gate2/s2-acquisition-admission-review-2026-11-15.md)、
[原容量契约](../../../research/phase-0.9.19/gate2/capacity-contract-proposal.md)、
[原容量/性能计划](2026-11-15-attribution-capacity-performance-plan.md)。

状态：**DESIGN_ONLY / CONDITIONAL_BYTE_BUDGET / RUNTIME_NOT_PROVEN**，2026-11-15。
本轮只有方案、来源核对和小整数算术，没有实现、回放、重评分、重冻结或模型调用。

## 1. 推荐决议

提出 `DC-EC-1` 单一候选供审核，**不宣称 R-C 已闭合或已有可启用路径**：

1. 不再要求客户端在未限定交付/缓冲的情况下，用有限存储完整接收任意交付。
   为未来新运行版本规定有界、可追溯的客户端交付域。
2. 增加交付次数与空交付工作量保护，明确它们会新增环境截尾；不是无行为变化优化。
3. 将单 capture 与 transport channel 的容量分开，按控制记录、metadata、派生输出、
   Base64、封套、结果文件及整批预算联合证明，不能只调一个 4 MiB 数字。
4. 保持原 v4 的提交/恢复/全审计语义，先检查这一最小改动方向是否可承担全部资源。
   如果必须改变布局或全量物化算法才可行，停止本候选并另案审议，不自动引入外存
   索引、增量审计、v6 或新架构。

不推荐只增大存储：它不能给 Q/客户端内存提供保证。不推荐只加 read 上限：它不能
保证越限片段和 terminal 能归档。联合候选的必要代价是**显式缩小支持的交付域**。
若 Owner 不接受这个变化，应保持当前不准入，而不是把限制隐藏在工程配置中。

## 2. Global Constraints：原样保留

- 研究问题、R2、C1/C2/C3、A/B 同次生成、D 仅诊断、UNRESOLVED、两轨分离不变。
- 公有语料、oracle、四份 prompt、576 槽位 schedule/seed/顺序均保持冻结原字节。
- 旧分数、全部历史与失败证据、S1/S2 结果不覆盖；P-G **620->496、20%、FAIL** 保留。
- live admission **W=1,048,576 B**；output 16384 tokens、input 131072 bytes、
  generation 180000 ms、cleanup 5000 ms 不变；不扣除写盘/审计时间续时。
- raw-first、每次实际 read 的边界、同步耐久确认、关键全历史审计、原错误事实保留。
- 无重试、补发、重排、恢复已 halted 批次；不把 541 个未发送坐标当作可续用额度。
- 不改变研究 GO 门槛或 v5/v6 原验收门槛；不重启计数优化或原性能系列。
- 不改实现、正式 Host/Graph/main；不重新冻结、不启动模型批次。以下数值均未启用。

## 3. 必须明确批准的变化

| 项目 | 当前情况 | DC-EC-1 候选 | 性质/影响 |
| --- | --- | --- | --- |
| 交付边界 | native Fetch response.body，单次 Q 与内部驻留未知 | 新版有界客户端的 HTTP body 交付接口，Q<=64 KiB，协议缓冲 F<=8 MiB | 更换/限定客户端，不能称旧运行身份不变；必须有分配前保证 |
| HTTP 编码/头 | 既有客户端解码及头处理 | identity-only；总头字节<=64 KiB、头项<=256；实际请求头变更需记录 | 新受支持传输域；非 identity/头越界属于新增环境失败 |
| 非空交付数 | 没有额外 read-count stop | 每次 generation 接受最多 N=32768 个非空交付；下一交付完整归档后报错 | 新失败边界，可能在 raw<1 MiB 时停止 |
| 空交付数 | 不增加 raw 字节，但工作量未界定 | 最多 1024 次非终止空交付，下一次报错；EOF 不计 | 新工作量边界；非空数与空数不得混用 |
| 单 capture | 与 channel 共用 4 MiB 限制 | 独立上限 16 MiB，支持完整 terminal/control | 要改容量校验/新 manifest 描述，不是旧 v4 零修改 |
| transport channel | 4 MiB | 64 MiB/attempt | 不删除 metadata；包含控制记录与失败处置空间 |
| wire/model/reasoning | 各 4 MiB | 各仍 4 MiB | wire 保存越限/cleanup，不能把 4 MiB 误当 live admission |
| 运行证据额度 | 未闭合 | 每 attempt 256 MiB；整批磁盘规划 192 GiB | 新容量申请，不是原 16 GiB 性能系列额度 |
| 失败分类与绑定 | 既有错误/协议版本 | 新域失败不可伪装成 D2 deadline censor；绑定交付与预算描述符 | 只加独立版本事实；原非 deadline 错误仍否决继续 |

N 的选择从 **32 MiB metadata 预算 / 1 KiB 每交付证明目标**得到 32768，额外预留
越限/cleanup 记录；不是从 r4 的 5667 或历史最大 read 882 B 反推阈值。
Q=64 KiB 与 F=8 MiB 是候选资源目标，不是从文件审计 64 KiB 读取块推出的网络保证。
空交付、头大小等同样是提议的新域条件，不是声称所有服务天然满足它们。

上述都必须另行明确批准，不能以“研究材料没变”冒充实验条件没变。若仅允许改变
存储数字、不允许限定交付域，本候选不成立。

## 4. 交付契约：先有可证明的接收端，再谈归档

### 4.1 客户端证明对象

未来实现必须在 allocation/交付之前约束接收链，而非拿到一个任意大 Buffer 后切片：

- 精确列出应用读取缓冲、HTTP/TLS 队列、解码队列、自动预取、连接池及关闭中的驻留。
  F 覆盖客户端协议栈内存，不含 Node 基础堆、账本和 OS 内核缓冲；后者仍须另计。
- 最多一个 owned read；有界预取，禁止未受控后台持续排队。不得为获得较大 read
  等待填满 Q，也不得跨交付合并来少写 metadata。
- 保持路径、模型、请求正文和生成参数不变；禁止自动重试、重定向补请求或失败重连
  重发。identity 请求头是显式新增传输配置，不修改 prompt。
- identity-only 禁止隐式解压造成预算放大。头限制必须发生在有界解析中，不能先无界
  物化完整 headers 再检查。响应不符合契约时不进入正常正文解码。
- 原始证据边界仍是客户端 HTTP body 字节，不宣称保存了 TLS/HTTP packet bytes。
  新客户端的实际交付边界和时间全部记录，不冒充旧 Fetch 分片；旧记录绝不重分片。
  分别记录已在客户端缓冲、已交付、已耐久三种状态；终止时未交付的内部缓冲不
  冒充已归档或完整远端响应。接收域变更须明确审批，不能暗换“原始 read”的含义。

本轮没有指定某个库已满足这些要求。任何库的配置项、后置检查或单个观测都不足以
替代准确版本的实现/契约证明。找不到满足 Q/F/头/无隐藏重试要求的客户端就停止。

### 4.2 计数与停止状态机（提案，未实现）

1. 发送前核对交付/预算描述符、冻结材料及所需资源证据；未知证明项则不准入，
   不能通过一次真实请求探测资格。原调用账本预留和发送屏障不削减。
2. 非空交付首先原样记录 metadata 和 raw，按原逐记录耐久确认；成功后才检查域上限。
   generation 最多接纳 N 次，收到第 N+1 次先完整归档，再标记 delivery-count-limit，
   不解码该交付、不继续正常生成。
3. W 的原检查保持，不截断触发 W 的交付。如果 W 和次数同时越界，原 response-byte
   事实与新增次数事实都保留；按原错误优先原则处理，不能把普通错误覆盖成 deadline。
4. 空交付不伪装成带字节 read，不向 raw 通道写假数据；累计数量进入完整 terminal。
   第 1025 次非终止空交付触发域失败。EOF 与最后数据交付的契约须无歧义。
5. cleanup 仍只等待已有 owned read，不发新 read；已交付片段完整归档，不解码成
   成功输出。保守预留一次 cleanup 交付，不提前依赖与 overshoot 的互斥证明。
6. delivery/encoding/header/资源/证据错误全局停止，不能获得 D2 局部 censor 资格。
   只有原 deadline-only 的全部条件满足时，才沿用原 D2 行为。

若 Q/F 或编码上界被实际实现违反，属于契约/完整性故障，立即停止并如实记录
evidence incomplete/unknown；保留可保存的原数据，不宣称截掉的超大交付已完整。
预留失败空间只能保证其声明范围内的诊断，不能保存任意无界违规输入。
**“正常域内完整归档”与“域外故障诚实关闭”是不同的证明义务。**

## 5. 证据容量合同与条件算术

### 5.1 证明目标，不是已验证配置

| 符号 | 候选值/定义 | 必须证明的来源 |
| --- | --- | --- |
| W/Q/N | 1048576 / 65536 / 32768 | W 原规则；Q 为实际客户端保证；N 为新域规则 |
| N_all | N+2=32770 | N+1 次越限 + 最多一次 cleanup，允许保守重复预留 |
| M | 每条 delivery metadata <=1024 B | index、phase、hash、时间数值和 JSON 精确最大编码 |
| C | 四类控制记录合计 <=16 MiB | pre_send<=4 MiB、request<=256 KiB、response<=256 KiB、terminal<=11.5 MiB |
| D | model+reasoning 合计 <=W | 当前 decoder 每个不重叠 content 字符串仅发一次，UTF-8/escape 变换全覆盖 |
| E | 非空派生记录数 <=floor(W/12)=87381 | 每个发出的字段占至少 12 个互不重叠原始 JSON 字节；需覆盖 escaped key/Unicode/跨 SSE 行 |
| R | reserve 内请求副本 <=1 MiB | 沿原账本请求限制，不能漏计该副本 |
| H | 每逻辑记录非 payload 的 JSONL 开销 <=1024 B | 全部控制/数据记录、seq/digest/坐标/金额/换行逐项证明，不能用平均数 |
| X | 每 attempt 外部请求/结果/诊断等 <=16 MiB | 原结果字段完整，不以截断日志或少保留对象实现额度 |
| F | 客户端协议缓冲 <=8 MiB | 分配前对象/队列证明；不是 RSS 总预算 |

C、D、E、H、X 的值均为**待证明目标**。若实际完整记录超过目标，不允许裁字段、
缩写 terminal、删 reasoning 或忽略未知 usage 来满足它。证明失败即拒绝候选，任何
改值另报，不在实现时自动放大。发送前控制记录也需覆盖其构造/编码峰值，不能靠
编码完成后的字节检查倒推内存有界。

### 5.2 小整数核算

当前 raw-first 路径只将检查 W 后的 generation 字节送入 decoder，故在契约成立时：

```text
B_raw <= W + 2Q                         = 1,179,648 B
T <= (N+2)*M + C                        = 50,333,696 B  (<64 MiB)
L <= 6 + 2*(N+2) + E                    = 152,927 records
P <= B_raw + T + D + R                  = 53,610,496 B
B64 <= 4*ceil((P + 2L)/3)               = 71,888,468 B
J <= B64 + L*H + X + 65,536             = 245,328,468 B
attempt allocation                     = 268,435,456 B  (256 MiB)
conditional margin                     = 23,106,988 B
```

Base64 上界按每条记录独立 padding 推导：每条长度 b 的编码为 4*ceil(b/3)，
不把总字节直接乘 4/3；上述最多 L 个 payload 的余量覆盖了独立边界。6 是当前
reserve/settle 和四类控制记录，不允许未来增加持久化事件却沿用 L；新增 failure
descriptor 若放进现有 terminal，其完整字节也必须计入 C。

该算式用于原 JSONL 容器，不套用 v6 二进制 144 B 封套，不改变提交次数。
这是条件数值一致性检查，不是调用 capacity evaluator 得到的新 PASS，更不证明
客户端、操作系统、JS 对象、磁盘或审计时间满足这些前提。

### 5.3 全批磁盘申请规模

不缩减原 576 槽位，不把 D 再乘一次，也不靠提前磁盘耗尽凑预算：

| 项 | 规划额度 |
| --- | ---: |
| 576 × 256 MiB，每槽完整候选额度 | 144 GiB |
| 共享描述符、源码、冻结引用及批报告 | 8 GiB |
| 独立失败/封存保留 | 8 GiB |
| 未分配余量 | 32 GiB |
| **联合磁盘规划** | **192 GiB** |

这些是新增采集容量规划，不是原 16 GiB/30 子进程性能系列预算。旧证据占用不含在
上述可用额度中，不能删除或迁移旧证据腾出空间。本轮不检查/预留磁盘、不请求额度。
未来需要对本次所有权目录提供可用空间/配额/失败保留与外部占用的保证；瞬时 free
值不是预留。正常域也可能遇到真实存储故障，该故障必须保留并停止。

## 6. 可行性分层：有数值预算不等于本机能运行

| 层次 | 本轮判断 | 下一步的决定性证据 |
| --- | --- | --- |
| 旧约束全部不改 | **不可行结论保留** | 无界 Q 未解；逐字节 metadata 原反例仍超 4 MiB |
| DC-EC-1 字节算术 | **条件一致** | 给定 Q/N/M/C/D/E/H/X 时单槽小于 256 MiB |
| 真实交付实现 | **未证明** | 分配前 Q/F、头/编码、队列、隐藏请求及 cleanup 保证 |
| 精确编码/派生界 | **未证明** | 不遗漏任何记录/字段的上界及全部反例 |
| 全历史内存/审计 | **未证明，主要现实风险** | 全量快照、解析和副本同时驻留；全部边界审计的累计成本 |
| 当前本机可运行/可采集 | **不准入** | 上述证据与单独审批均缺，192 GiB 只是磁盘规划 |

原 v4 路径仍会读取/物化完整历史；每 attempt 有界并不能给整个 576 槽位过程带来
恒定 RSS。必须列出完整 JSONL 字符串、split/parse 对象、attempt/chunks、snapshot
克隆、当前响应/terminal、下一轮历史和请求编译的同时驻留集合。不能拿 F=8 MiB、
一个 read 的 Q 或旧“6*J”估算充当 V8/进程内存证明。

同样，保留完整审计意味着实际扫描成本至少覆盖每个审计边界的全部历史 B_k，即
sum(B_k)。磁盘总额 192 GiB 不是累计审计读量；原 P-H/P-G 额外扫描不消失。
本方案不填假定 RSS 数字或给出“18 小时能跑完”的承诺。资源上界未证明就是
INCOMPLETE；只有具体允许输入超过资源的证据才能升级为该资源域 INFEASIBLE。

若保持原 v4 物化/审计语义后，准确证明显示本机无法承担，**本候选在本机退出**。
这时不能偷偷引入 stream audit/index/sidecar 来“完成本方案”，也不能减少原全批
预算或增加未批的磁盘提前停止。新架构或不同受支持资源环境须另案，旧门槛不消失。

## 7. 对两个原反例的处理，不撤销失败

- 原 3,145,729 B 单交付超过候选 Q：新客户端必须在其实际交付接口的分配/交付前
  提供界，而不是事后把旧片段切成 64 KiB。当其底层确实接收同一长字节流时，
  新的真实交付须全部留痕；旧 trace 不改。新接口未证明前，反例仍然阻塞。
- 原 1 MiB 逐字节交付：在候选中第 32769 次非空交付归档后停止，最多再保留一个
  cleanup 交付。因此它是**新环境截尾**，不是把旧 180,292,538 B 证据重新压成成功。
- 若禁止这种 read-count 截尾，原逐字节域必须完整保留；仅 transport 4 MiB 就不够，
  本候选的 N/T/J 推导失效，需要另案全域容量证明，不能自动切到另一个上限。

## 8. 研究效度与报告要求

- 同次生成的 H1 不变；新限制可能改变可观察输出，必须带独立 environment/profile
  版本，分别报告 C1/C2/C3、A/B/C0/D 的已发送、完整、域截尾、证据故障与未发送数。
- delivery-count 等截尾保留在已发送/完成率分母；缺完整输出的语义成绩按原规则
  保持不可得，不能补成失败分数或从统计表删除。发送前拒绝与已发送截尾分开。
- 所有条件/臂统一应用，不能为困难、C3、D2 或长状态单独加额度。新环境结果不能
  与 r1-r4 混成一个提高后的成功率；不能将失败输出换新环境重跑来修正旧成绩。
- 新客户端的交付、背压、编码选择影响延迟和 deadline 内可见量。真实 streaming、
  首正文和成本门槛照旧，不能通过填满缓冲后批量播放假装流式。
- 请求正文、prompt/oracle/schedule 字节不变不等于最终请求/运行身份相同。新增
  Accept-Encoding 和交付描述符、源码、错误策略以后都须单独冻结；本轮不冻结。
- S1 的 lifecycle/引用及身份标签问题、S2 的 18 次前缀版本问题仍独立存在；容量
  设计不会修复或隐性批准它们，不改分、不补跑前缀。
